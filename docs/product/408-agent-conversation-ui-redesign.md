# 408 Agent 对话界面重设计

> 版本：v0.3
>
> 日期：2026-07-23
>
> 状态：已完成 Agent 动态路由语义复审，作为后续实现基线
>
> 适用范围：用户端 `/agent`、`/agent/{thread_id}`

## 1. 设计结论

Agent 页面应从“单次运行结果报告页”改成“持续对话页”。

页面的唯一主任务是：**让用户在同一个对话上下文中提问、看到实时回答、理解 Agent 正在执行什么，并在需要时完成补充、审批或重试。**

本次重设计采用“安静的执行对话”方向：

- 借鉴成熟聊天产品的居中消息流、稳定输入区和低干扰排版。
- 用户消息使用轻量气泡，Agent 回复使用自然正文，不再使用文章首页式标题和栏目。
- 用户始终从统一对话入口发送自然语言，不在开始时选择或预设 workflow。
- Agent 对每一轮输入结合 thread 历史、附件、引用和已有执行结果，动态决定直接回答、澄清或调度业务 workflow。
- workflow 作为对话内容的一部分，按实际发生位置插入消息流，可在同一线程中出现多次。
- workflow 默认只显示一行安全摘要；用户展开后才看到公开步骤、状态、耗时和结果摘要。
- 引用证据可以继续使用右侧抽屉，但右侧不再常驻展示执行链路。
- 回答正文只保留有限、统一的 Markdown 层级，不让模型输出决定页面视觉层级。

## 2. 设计对象

### 2.1 具体产品对象

- 产品：408 学习 Agent。
- 用户：正在备考计算机 408、会连续追问、做题、批改和调整学习计划的学习者。
- 场景：一次线程可能持续数天，普通问答和 Agent 动态调度的 workflow 会交替出现。
- 页面任务：维持上下文连续性，让用户始终知道“我说了什么、Agent 回了什么、执行到了哪里、现在要不要我操作”。

### 2.2 不再采用的页面隐喻

现有页面同时使用大标题、眉题、报告卡、证据栏目、执行侧栏和结果摘要，形成了“文章/报告”的阅读隐喻。它适合展示一次固定结果，不适合持续对话。

新页面不再把一次 run 当成整页主角，而是把 thread 当成主角。run、workflow、artifact、approval 都是 thread 时间线中的内容。

## 3. 现状问题审计

### 3.1 页面结构问题

当前 [AgentPage.tsx](../../frontend/src/pages/AgentPage.tsx) 的主要问题：

1. 页面只选择最新 run，中央区域只渲染该 run 的用户输入和结果，历史对话没有形成连续消息流。
2. `waiting_for_user` 和 `waiting_for_approval` 通过提前 `return` 切换成独立页面，用户会失去此前对话上下文。
3. workflow 执行轨迹常驻右栏；屏幕宽度不足时再变成抽屉，执行内容与触发它的消息分离。
4. 完成态使用“直接结论”眉题、23px 衬线标题、大段来源区和操作区，更像文章详情页。
5. 运行态、失败态、审批态都使用大块报告卡，连续多次运行时会形成视觉噪音。
6. 页面存在硬编码证据、步骤和失败结果，真实 run 与展示内容尚未统一。

### 3.2 字体与内容层级问题

当前 Agent 区域同时使用：

- 衬线字体的大标题。
- 无衬线正文。
- 等宽字体的序号和耗时。
- `eyebrow` 全局眉题。
- 多种 9px、10px、11px、13px、15px、20px、23px 字号。

这会让同一条回复被拆成多个视觉栏目。新设计要求聊天内容区最多只有三级文本强度：正文、正文内小标题、元信息。

### 3.3 workflow 位置问题

workflow 是由某条用户消息或某个 Agent 建议触发的过程，因此应紧邻触发点。如果始终放在右栏，用户无法回答以下问题：

- 这是哪次追问触发的 workflow？
- 线程中第二次 workflow 与第一次有什么区别？
- 审批和失败属于哪一次执行？
- 刷新后应该恢复到哪一个执行块？

因此本设计取消“右侧执行轨迹”这一主结构。

## 4. 设计原则

### 4.1 对话优先

消息顺序高于页面栏目。用户消息、Agent 消息、workflow、审批、澄清和错误按照发生顺序进入同一个滚动流。

### 4.2 同一内容字体体系

模型输出不能直接制造页面级视觉层级。无论模型返回多少级 Markdown 标题，客户端都要映射到受控的对话排版。

### 4.3 执行过程就地出现

workflow 必须出现在触发它的对话位置。右侧区域只用于用户主动打开的证据、引用原文或线程信息。

### 4.4 默认简洁，按需展开

普通用户首先看到“正在做什么”和“结果是什么”。工具参数、步骤摘要、耗时和恢复信息放在展开层，不显示隐藏思维链。

### 4.5 服务端事实驱动

运行中、等待审批、失败、已完成等状态来自持久化 run 和事件，不用组件本地 `loading` 模拟。

### 4.6 长线程仍可扫描

已经完成的 workflow 自动收起，保留名称、结果、耗时和产物入口。当前运行、待审批和失败 workflow 保持展开或半展开。

### 4.7 Kimi / Claude 参考边界

本设计参考用户所指的 Kimi、Claude 类型聊天页的共同交互范式，而不是像素级复刻：

- 使用居中的单一消息主列，让问题与回答沿同一阅读轴连续出现。
- 输入区稳定停留在底部，线程切换、继续追问和长回答阅读都不改变页面基本结构。
- 用户消息可使用轻量气泡，Agent 正文保持开放排版，避免双方都被大卡片包裹。
- 产品操作、来源和执行信息保持低干扰，需要时再展开。

408 Agent 的差异点是 workflow：它不是独立侧栏，也不是隐藏的后台 loading，而是对话流中可恢复、可操作、可重复出现的执行节点。

### 4.8 统一 Agent 入口与逐轮决策

用户面对的是一个持续存在的 Agent，而不是一组需要预先选择的 workflow。每条用户消息都形成独立 turn，Agent 必须在服务端重新判断本轮下一步处理：

```text
用户输入
  ├─ direct_answer：普通问答，只显示 Agent 消息
  ├─ clarify：路由前信息不足，以普通 Agent 消息追问
  ├─ explain：启动讲解 workflow
  ├─ validate：启动验证练习 workflow
  ├─ grade：启动批改 workflow
  └─ plan：启动计划调整 workflow
```

产品层必须遵守以下边界：

- 输入区不暴露 workflow key、模式下拉框或 `preferred_action`。
- 建议按钮只负责填入或发送自然语言，例如“根据刚才的内容给我出三道题”，不能直接指定 `validate`。
- 路由前澄清是普通对话；只有 workflow 已启动后所需的结构化补充、审批和恢复操作才进入 workflow 块。
- workflow 完成后 thread 仍保持 active；后续输入重新走同一套动态决策，可以触发其他 workflow，也可以回到普通问答。
- conversation/router 属于内部执行机制，不向用户展示“意图识别”“选择处理方式”等内部步骤。

## 5. 视觉方向

### 5.1 方向名称

**安静的执行对话 / Quiet Execution Chat**

界面整体接近一个可靠的日常对话工具，而不是知识文章、仪表盘或工作流编辑器。视觉个性集中在 workflow 的“执行脉冲条”，其余区域保持克制。

### 5.2 色彩令牌

| 令牌 | 色值 | 用途 |
|------|------|------|
| `chat-canvas` | `#F7F8FA` | 页面背景、减少纯白眩光 |
| `chat-surface` | `#FFFFFF` | 消息流、输入区和浮层 |
| `chat-ink` | `#20242B` | 主要文字 |
| `chat-muted` | `#667085` | 时间、状态和辅助说明 |
| `chat-line` | `#E6E9EE` | 分隔线、输入区边界 |
| `chat-accent` | `#4059D8` | 当前执行、链接、键盘焦点 |

语义色不参与品牌表达，只传达状态：

- 成功：`#2E7D5B`
- 等待：`#A46616`
- 失败：`#B54747`
- 用户气泡：`#EFF1F4`

### 5.3 字体系统

对话内容不使用衬线字体。

| 角色 | 字体 | 规则 |
|------|------|------|
| 对话正文与控件 | `Inter`, `PingFang SC`, `Microsoft YaHei`, sans-serif | 页面 95% 的文本使用此角色 |
| 数据与代码 | `JetBrains Mono`, `SFMono-Regular`, monospace | 仅用于代码、耗时、步骤计数，不用于正文标题 |

字号控制：

| 内容 | 桌面 | 移动 | 行高 |
|------|------|------|------|
| 对话正文 | 15px | 15px | 1.75 |
| 回复内小标题 | 16px / 600 | 16px / 600 | 1.55 |
| 消息元信息 | 12px | 12px | 1.4 |
| workflow 摘要 | 13px | 13px | 1.5 |
| 代码 | 13px | 12.5px | 1.65 |
| 页面/线程标题 | 15px / 600 | 14px / 600 | 1.4 |

禁止在对话正文中使用 20px 以上标题。页面品牌可有独立字体，但不进入消息流。

### 5.4 形状、边界和阴影

- 用户气泡圆角：16px，右下角 6px。
- 输入区圆角：18px。
- workflow 块圆角：12px。
- 普通内容卡圆角：10px。
- 边框统一为 1px；不使用双重边框和大面积彩色底。
- 主页面不使用大阴影；输入区悬浮时使用 `0 8px 28px rgba(24, 32, 56, 0.08)`。
- workflow 展开层使用浅色背景，不使用独立“大卡片海报”。

### 5.5 记忆点：执行脉冲条

workflow 块左侧放置一条 2px 的执行轨道：

- 运行中：轨道顶部有一个缓慢移动的蓝色脉冲点。
- 等待用户：脉冲停在当前步骤，变为琥珀色。
- 完成：轨道变为低饱和绿色，默认收起。
- 失败：停在失败节点，轨道末端为红色短线。

这是本设计唯一主动强化的视觉元素。它让 workflow 在聊天流中可识别，但不会把整个页面重新变成流程图。

## 6. 信息架构

### 6.1 桌面布局

```text
┌──────────────┬──────────────────────────────────────────────────────────┐
│ 左侧导航     │ 线程标题                         [引用/信息] [更多]      │
│              ├──────────────────────────────────────────────────────────┤
│ + 新对话     │                                                          │
│ 最近对话     │              conversation stream  760px                 │
│              │                                                          │
│ 今天         │         用户消息                                         │
│ Agent        │                         ┌──────────────┐                 │
│ 练习         │                         │ 轻量用户气泡 │                 │
│ 薄弱点       │                         └──────────────┘                 │
│              │                                                          │
│              │         Agent 回复正文                                   │
│              │         workflow 执行块                                  │
│              │         Agent 后续回复                                   │
│              │                                                          │
│              │         ┌────────────────────────────────────┐           │
│ 账户         │         │ 输入消息…                    发送  │           │
└──────────────┴─────────┴────────────────────────────────────┴───────────┘
```

布局规则：

- 保留现有左侧导航和最近线程能力。
- 主消息列最大宽度 760px；宽屏时居中，不拉伸成文章长行。
- 线程头部高度 52–56px，只显示标题、同步状态和辅助操作。
- 输入区与消息列同宽，底部吸附，不跨满整个工作区。
- 默认无右栏。点击引用、原题或线程信息时，以 380–420px 抽屉打开。

### 6.2 移动布局

```text
┌──────────────────────────────┐
│ ‹ 对话列表   循环队列   ⋯    │
├──────────────────────────────┤
│                              │
│                  用户气泡    │
│                              │
│ Agent 回复                   │
│ ┌──────────────────────────┐ │
│ │ workflow · 正在生成练习  │ │
│ │ 2/4 · 正在筛选题目       │ │
│ └──────────────────────────┘ │
│                              │
│ Agent 回复                   │
│                              │
├──────────────────────────────┤
│ ＋  输入消息…          ↑     │
└──────────────────────────────┘
```

- workflow 与桌面使用同一组件，不改成独立全屏步骤页。
- 引用和 workflow 详细信息使用底部抽屉。
- 输入区考虑安全区，不遮挡最新消息。
- 底部全局导航在键盘弹出时隐藏。

### 6.3 新对话空态

新对话页仍然是聊天页，不做大幅 hero：

- 主输入区位于首屏垂直中心略上方。
- 标题使用 22px：“今天想解决什么问题？”
- 下方只保留 3 个简短建议，不展示大段能力宣传。
- 不提供 workflow 选择器。系统在服务端识别意图；斜杠命令或建议动作如后续提供，也只能转成自然语言意图，不能绕过 Agent Router 直接指定 workflow。

## 7. 对话流模型

### 7.1 顶层节点

对话流只允许以下顶层节点：

| 节点 | 视觉形式 | 是否可重复 |
|------|----------|------------|
| 用户消息 | 右侧轻量气泡 | 是 |
| Agent 消息 | 左侧自然正文 | 是 |
| workflow | 左对齐内嵌执行块 | 是，同一线程可多次出现 |
| 系统状态 | 居中单行弱提示 | 是 |

审批、workflow 执行中的结构化补充、错误和产物默认属于某个 workflow，渲染在该 workflow 块内部或紧随其后，不切换成独立页面。路由前澄清属于普通 Agent 消息，不创建可见 workflow 块。

### 7.2 消息分组

一次用户输入及其后续响应形成一个 turn group：

```text
用户消息
  ├─ Agent 直接回答或澄清（可选）
  ├─ Agent 动态调度的 workflow A（可选）
  │    ├─ 澄清（可选）
  │    ├─ 审批（可选）
  │    └─ 产物/错误（可选）
  └─ Agent 最终回复
```

下一次用户输入会形成新的 group。一个线程中可以出现：

```text
用户提问 → 讲解 workflow → Agent 回答
用户追问 → Agent 直接回答
用户要求出题 → 练习 workflow → 练习产物
用户提交答案 → 批改 workflow → 反馈
用户要求调整计划 → 计划 workflow → 审批 → 结果
```

### 7.3 Agent 消息

Agent 消息不使用完整气泡，不使用大标题卡。结构为：

```text
[Agent 标记] 408 Agent · 刚刚

正文第一段……

小标题
正文、列表、公式或代码……

[1] [2]                    复制  有帮助  没帮助
```

规则：

- 头像或标记仅在一组连续 Agent 内容的第一项显示。
- 流式输出时不显示“正在加载回答内容”，而是在真实消息位置追加文本。
- 完成后出现复制、反馈、重试等弱操作。
- 引用标记贴近结论；来源列表不默认占据整块正文。

### 7.4 用户消息

- 最大宽度为消息列的 72%。
- 附件在气泡上方或内部以紧凑文件行显示。
- 时间默认隐藏，悬停、聚焦或长按后显示。
- 发送失败时在气泡下方显示“未发送 · 重试”。
- 当前 workflow 运行时继续发送的消息，若后端采用排队策略，气泡下方显示“已排队，将在当前任务完成后处理”。

## 8. workflow 内嵌设计

### 8.1 收起态

```text
┃  ✓ 已生成 3 道循环队列练习                    18 秒  ›
┃    已检索 18 道候选题并通过质量检查
```

收起态只展示：

- 公开名称，不显示内部 workflow key。
- 当前/最终状态。
- 一句安全摘要。
- 总耗时或当前进度。
- 展开按钮。

完成的 workflow 默认收起；用户手动展开状态在当前会话内保留。

### 8.2 运行态

```text
┃  正在生成专项练习                                      2/4
┃  ━━━━━━━━━━━━━━━━░░░░░░░░
┃  正在检查题目质量…
┃
┃  [查看步骤]                              [停止]
```

运行态不展示每一个模型 token 或内部节点闪烁。公开进度只在阶段变化或摘要变化时更新。

### 8.3 展开态

```text
┃  正在生成专项练习                                      2/4
┃
┃  ✓ 找到相关考点                         1.2 秒
┃    已定位“循环队列下标关系”及两个相邻考点
┃
┃  ● 筛选可靠题目                         执行中
┃    正在检查题干、答案和选项完整性
┃
┃  ○ 组合练习
┃  ○ 保存练习
┃
┃  [收起步骤]                              [停止]
```

展开后只允许展示：

- 用户可理解的步骤名称。
- 输入范围摘要。
- 结果摘要。
- 状态、耗时、是否发生重试。
- 可恢复动作。

不得展示模型隐藏推理、完整 prompt、原始工具参数、密钥、其他用户数据或未裁剪日志。

### 8.4 等待用户

澄清控件直接放入 workflow 块：

```text
┃  需要你确认练习方式
┃  你想先看讲解，还是直接做题验证？
┃
┃  [先讲解]  [直接做题]
┃  也可以补充说明…
```

选择后原位置变为“你选择了：直接做题”，workflow 继续运行，不产生独立页面跳转。

### 8.5 等待审批

```text
┃  需要确认：调整本周学习计划
┃  原因：循环队列连续两次验证未通过
┃
┃  周三：操作系统 30 分钟   →   循环队列 20 分钟
┃  周四：循环队列 10 分钟   →   操作系统 20 分钟
┃
┃  可撤销 · 拒绝后不影响当前对话
┃  [保持原计划]  [采用调整]
```

审批完成后保留决定结果，不删除审批节点。

### 8.6 失败与重试

```text
┃  ! 生成练习时中断
┃    已保留：考点定位、18 道候选题、3 道练习草稿
┃    失败：生成逐题提示时超时
┃
┃    [重试失败步骤]  [使用已保留结果]
```

失败块必须清楚区分：

- 已完成并保留的内容。
- 未完成的步骤。
- 重试范围。
- 是否会产生重复写入。

### 8.7 同一线程多次 workflow

- 每次 Agent 根据新 turn 决定启动业务任务时生成新的 workflow 块；用户不直接选择 workflow 类型。
- workflow 块固定在触发消息之后，不因后续状态更新移动位置。
- 相同类型 workflow 也分别显示，例如“专项练习 · 第 1 次”和后续的“错题再练 · 第 2 次”，但默认不使用机械编号；优先用任务名称区分。
- 子 workflow 默认折叠进父 workflow 的公开步骤，除非它本身需要用户操作或产出独立可使用结果。
- 一个 workflow 完成后，后续对话不能把它重新改为运行中；重试应生成 attempt 或新 run 关系，并在原块内显示“第 2 次尝试”。

## 9. 内容与 Markdown 规则

### 9.1 允许的格式

- 普通段落。
- 最多两级回复内标题。
- 有序和无序列表。
- 行内代码和代码块。
- 引用块。
- 公式。
- 简单表格。
- 引用标记。

### 9.2 视觉归一化

| 模型内容 | 客户端表现 |
|----------|------------|
| `# H1` | 映射为 16px/600 的回复内标题 |
| `## H2`、`### H3` | 映射为同一层级或 15px/600 |
| 连续多个标题 | 合并间距，不形成文章目录感 |
| 粗体整段 | 降为普通正文，仅保留语义重点 |
| 超宽表格 | 水平滚动，不扩大消息列 |
| 代码块 | 统一 13px，提供复制按钮 |
| 过多分割线 | 只保留必要分段，其余忽略 |

### 9.3 间距

- 段落间距 12px。
- 小标题上间距 20px，下间距 8px。
- 列表项间距 4px。
- 不同顶层消息间距 24px。
- 用户消息与其 workflow/回复组间距 16px。
- 完成 workflow 收起后高度控制在 52–68px。

## 10. 输入区

### 10.1 默认结构

```text
┌────────────────────────────────────────────────────────┐
│ 输入消息，粘贴题目，或描述要执行的学习任务…           │
│                                                        │
│ ＋  引用当前内容              模型/范围状态       ↑     │
└────────────────────────────────────────────────────────┘
```

- `Enter` 发送，`Shift + Enter` 换行；中文输入法组合期间不得误发送。
- 附件、引用、可选动作放在左侧。
- 发送按钮在无内容时禁用，运行中不替换成全局 loading。
- 不展示 workflow 下拉框、处理模式或其他直接指定执行链路的控件。
- 输入内容自动增高，桌面最高 220px，移动最高 160px。

### 10.2 运行中继续输入

界面不得承诺“会在当前步骤后处理”，除非后端已经实现消息排队。

目标行为：

1. 用户发送后立即出现消息气泡。
2. 后端将其标记为 `queued` 或创建新的 turn。
3. 气泡下显示真实状态。
4. 用户可以取消尚未执行的排队消息。

如果第一阶段未实现排队，则运行中输入区应明确提示“当前任务完成后可继续发送”，而不是产生并发 run。

## 11. 滚动与流式输出

- 用户发送后滚动到该条用户消息，使问题和回答起点同屏。
- 当用户距离底部不超过 120px 时，流式文本自动跟随。
- 用户向上阅读后停止自动滚动，并显示“回到最新”按钮。
- workflow 状态更新只修改对应块，不让整个列表重新排序。
- 流式 Markdown 以稳定块渲染，未闭合代码块和公式先按纯文本处理，完成后再升级格式。
- 页面刷新后先恢复持久化时间线，再连接事件流；不能先显示空白页。

## 12. 引用与证据

- 正文引用使用 `[1]` 或紧凑来源标记。
- 点击引用后打开右侧抽屉，并定位到支撑当前结论的片段。
- 抽屉关闭后返回原滚动位置。
- workflow 的步骤详情不能与证据抽屉混为一体。
- 来源不足时使用“模型推断”文本标记，不使用伪造引用。

## 13. 线程头部与左侧导航

### 13.1 线程头部

只保留：

- 返回/折叠导航。
- 线程标题。
- 保存或同步状态（仅异常时显著）。
- 引用/线程信息入口。
- 更多菜单：重命名、归档、删除。

不在头部持续显示“运行中/已完成”大状态。当前运行状态应出现在对应 workflow 块中。

### 13.2 最近线程

- 紧凑单行列表。
- 标题最多两行。
- 当前线程使用轻底色和字重表示。
- 运行中线程可显示 6px 状态点，不显示完整进度条。
- 列表按最近活动时间排序，而不是创建时间。

## 14. 响应式与可访问性

- 断点建议：`< 768px` 移动，`768–1180px` 紧凑桌面，`> 1180px` 标准桌面。
- 所有图标按钮必须有可访问名称和可见焦点。
- workflow 展开按钮使用 `aria-expanded` 和 `aria-controls`。
- 状态不能只依赖颜色，同时使用文字和图标。
- 动画尊重 `prefers-reduced-motion`；关闭后脉冲点改为静态状态点。
- 流式输出区域不应逐 token 触发屏幕阅读器；按句或完成后使用受控 live region。
- 输入、审批和重试操作支持键盘完成。

## 15. 自我评审与取舍

初版方案曾考虑保留“右栏步骤 + 中央回答”的学术工作台结构，但这仍然以单次 run 为中心，无法自然表达同一线程中的多次 workflow，因此移除。

初版视觉也考虑继续使用衬线标题来保留“学习产品”气质，但它会放大文章感，违背本次核心目标。因此 Agent 对话区完全改用同一无衬线字体体系；产品识别度改由执行脉冲条和内容可信设计承担。

“执行脉冲条”是本设计唯一的视觉风险：它比普通聊天产品更突出运行过程。保留它的理由是本产品不是纯聊天工具，用户需要理解 workflow 的存在、等待和恢复；风险通过默认收起、低饱和色和有限动效控制。

## 16. 从现有页面到目标页面的组件映射

| 现有结构 | 目标结构 | 处理 |
|----------|----------|------|
| `agent-workspace` 两栏 | 单列 conversation workspace | 移除常驻右侧 workflow 栏 |
| `agent-thread__header` 大标题状态 | 轻量线程头部 | 去掉页面级 run 状态 |
| `user-entry` | `UserMessage` | 保留气泡思路，去掉固定头像占位 |
| `run-summary` | `WorkflowBlock` | 改为内嵌、可重复、可折叠 |
| `ExecutionTrace` | `WorkflowSteps` | 作为 workflow 的展开内容 |
| `agent-answer` | `AssistantMessage` | 去衬线大标题和报告栏目 |
| `approval-sheet` 独立页 | `WorkflowApproval` | 嵌回对应 workflow |
| waiting 独立页 | `WorkflowClarification` | 嵌回时间线 |
| `agent-context` | `EvidenceDrawer` | 仅按需打开证据 |
| workflow `<select>` | 服务端自动路由/建议动作 | 默认输入区移除 |

## 17. 高保真必须覆盖的画面

1. 新对话空态：桌面与移动。
2. 普通问答流式输出。
3. 一次对话中出现两个不同 workflow。
4. workflow 收起、运行、展开、完成。
5. workflow 等待结构化补充。
6. workflow 待审批和审批完成。
7. workflow 失败、部分结果保留和局部重试。
8. 长回答、代码、公式、表格和引用。
9. 用户向上阅读时继续流式输出。
10. 断线重连和刷新恢复。

## 18. 设计验收标准

- 首屏能明确判断这是聊天界面，而不是文章详情页。
- 用户可以在不查看右栏的情况下理解当前 workflow 的状态。
- 同一线程连续出现 3 次 workflow 时，仍能明确对应到各自触发消息。
- Agent 正文的最大字号不超过 16px，除代码外只使用一个主要字体体系。
- 已完成 workflow 收起后不会压过后续对话内容。
- 等待用户、待审批和失败状态不离开当前时间线。
- 流式输出不会反复跳动、自动抢滚动或造成标题层级突变。
- 桌面 1280px、1440px 和移动 390px 下输入区均不遮挡最新消息。

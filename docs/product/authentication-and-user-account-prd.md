# 用户认证与账户系统 PRD

> 状态：方案评审稿
> 最后更新：2026-07-16
> 范围：408 学习工作台用户端认证、账户、会话和用户数据归属
> 不包含：本轮不进入编码；管理员认证只定义边界，不在本 PRD 中重做

## 1. 决策摘要

当前用户端并没有真实认证：浏览器只在 `localStorage` 或 `sessionStorage`
中保存 `starmap.authenticated=true`，任何人都可以自行伪造。后端公开的
`/api/v1/chat` 和 `/api/v1/chat/{session_id}/history` 也没有用户认证与
对象级授权。现有 `user_question_records` 只关联临时 `session_id`，不能证明
记录属于哪个真实用户。

因此登录模块不能只实现一个登录表单，而要同时建立以下四个边界：

1. **身份边界**：服务端能够可信地判断当前用户是谁。
2. **会话边界**：登录状态可过期、可撤销、可查看、可跨设备管理。
3. **授权边界**：用户只能访问自己的对话、练习、错题、资料和学习记录。
4. **数据归属边界**：所有用户私有业务记录都绑定稳定的内部 `user_id`，不绑定
   邮箱、GitHub 用户名或浏览器会话。

首发必须支持：

- 邮箱和密码注册。
- 注册邮箱验证与重发。
- 邮箱和密码登录。
- GitHub 快速注册/登录。
- 忘记密码与重置密码。
- 当前登录状态恢复、退出登录、退出全部设备。
- 用户基本资料维护。
- 前端路由保护和后端 API 强制认证。
- 所有用户私有资源的对象级授权。
- 登录限流、撞库防护、会话安全、审计与账号停用。

建议但可在后续迭代交付：

- 设备和登录会话管理页。
- 登录提醒与异常登录告警。
- Passkey、TOTP 和恢复码。
- 账号数据导出与自助注销。
- 用户主动绑定/解绑更多登录方式。

## 2. 产品目标

### 2.1 用户目标

- 用户能用邮箱或 GitHub 快速进入学习工作台。
- 用户换设备或刷新页面后，仍能恢复自己的学习状态。
- 用户能够识别、维护和保护自己的账号。
- 用户无法看到其他人的任何私有学习数据。
- 用户丢失密码时可以安全恢复账号。

### 2.2 系统目标

- 建立全系统唯一、稳定、不可由用户修改的内部用户标识。
- 为对话、练习、错题、掌握度、计划、资料和 Agent 运行提供统一归属。
- 支持账号停用、会话撤销、密码重置、外部身份解绑和账号删除。
- 不依赖前端状态判断安全性。
- 不将认证令牌放入浏览器 `localStorage` 或 `sessionStorage`。
- 保留未来接入 Passkey、更多 OAuth 提供方和移动端的扩展空间。

### 2.3 成功指标

产品指标：

- 注册提交到邮箱验证完成率。
- 邮箱投递成功率和验证链接打开率。
- GitHub 登录完成率。
- 登录失败率及失败原因分布。
- 忘记密码流程完成率。
- 新用户登录到完成 onboarding 的转化率。

安全和稳定性指标：

- 未认证访问私有 API 的拦截率应为 100%。
- 跨用户对象访问自动化测试通过率应为 100%。
- 被限流的暴力登录、验证码轰炸和重置邮件轰炸次数。
- 活跃会话数、异常会话撤销数和过期清理延迟。
- 认证接口 P95 延迟、错误率和邮件队列积压。

## 3. 非目标

首发不做：

- 企业 SSO、SAML、组织目录同步。
- 多租户组织、学校、班级和成员邀请。
- 社区账号、关注、排行榜和公开个人主页。
- 手机号和短信登录。
- 依赖安全问题找回密码。
- 用人脸、身份证等敏感个人信息做实名认证。
- 将 GitHub 仓库权限作为登录所需权限。
- 将管理员与普通学习用户放进同一个登录入口。

## 4. 角色与权限边界

### 4.1 匿名访客

允许：

- 访问登录和注册页面。
- 发起注册、登录、邮箱验证、忘记密码和 GitHub OAuth。
- 查看公开产品介绍。

禁止：

- 访问用户主页和任何学习工作台页面。
- 调用对话、练习、错题、资料、计划等用户 API。
- 读取任何指定 `session_id`、`thread_id` 或资源 ID 的私有数据。

### 4.2 待验证用户

允许：

- 查看“等待验证”状态。
- 重发验证邮件。
- 更换待验证邮箱，需重新校验密码或注册事务。
- 退出当前预认证状态。

禁止：

- 进入学习工作台。
- 创建对话、练习和长期学习记录。

### 4.3 已登录学习用户

允许：

- 访问自己的学习数据。
- 修改昵称、头像、时区等非敏感资料。
- 修改邮箱、密码、绑定身份等敏感信息，但必须近期重新认证。
- 查看和撤销自己的会话。
- 注销账号和申请导出数据。

禁止：

- 访问其他用户的数据。
- 调用管理员 API。
- 修改服务端认定的 `user_id`、账号状态和权限。

### 4.4 管理员

管理员属于独立安全域：

- 使用独立入口和独立认证策略。
- 普通用户登录不能获得管理员权限。
- 用户端和管理端可以由同一个后端应用提供 API，但必须使用不同的登录端点、会话
  Cookie、认证依赖和权限模型。
- 不允许在普通用户登录成功后仅根据 `role=admin` 自动跳转并升级为管理会话。
- 管理员可以停用用户和撤销会话，但不能查看密码、会话令牌或重置令牌。
- 查看用户私有学习内容需要单独定义运营权限和审计，不因“管理员”身份自动开放。

首发建议继续保留 `admin_users`，不要直接合并到学习用户 `users`。这样可以减少
普通用户认证漏洞向管理后台扩散的风险。同一个人同时是学习用户和管理员时，也使用
两个独立账号和两次独立认证；未来如需“以用户视角查看”，应实现短时、明确授权、
全程审计的模拟功能，不能复用普通登录进行隐式切换。

## 5. 术语

| 术语 | 定义 |
|------|------|
| 用户 | 产品内部的稳定账户主体，由内部 `user_id` 唯一标识 |
| 登录身份 | 用户用于证明身份的方法，例如密码或 GitHub |
| 外部身份 | GitHub 等第三方返回的稳定主体标识 |
| 会话 | 用户完成登录后，由服务端创建并可撤销的登录状态 |
| 预认证状态 | 已发起注册、OAuth 或敏感操作，但尚未完成全部验证 |
| 用户私有资源 | 对话、练习、错题、资料、计划、掌握度等归属于单个用户的数据 |
| 对象级授权 | 每次访问具体资源时校验该资源是否属于当前用户 |

## 6. 功能范围与优先级

### 6.1 P0：上线阻断项

| 编号 | 功能 | 验收摘要 |
|------|------|----------|
| AUTH-01 | 邮箱密码注册 | 邮箱唯一，密码合规，创建待验证账号 |
| AUTH-02 | 邮箱验证 | 单次、限时令牌；验证后激活账号 |
| AUTH-03 | 邮箱密码登录 | 通用错误提示、限流、创建服务端会话 |
| AUTH-04 | GitHub 登录 | Authorization Code + PKCE + state，服务端回调 |
| AUTH-05 | 当前用户 | 刷新后通过服务端 `/me` 恢复身份 |
| AUTH-06 | 退出登录 | 服务端撤销当前会话并删除 Cookie |
| AUTH-07 | 忘记密码 | 不泄露邮箱是否存在，邮件令牌单次限时 |
| AUTH-08 | 重置密码 | 更新密码，撤销既有会话，通知用户 |
| AUTH-09 | 前端路由守卫 | 只负责体验，不作为安全边界 |
| AUTH-10 | 后端认证守卫 | 所有私有 API 默认要求当前用户 |
| AUTH-11 | 对象级授权 | 所有资源按 `current_user.id` 限定查询 |
| AUTH-12 | 用户数据绑定 | 新增记录必须写入真实 `user_id` |
| AUTH-13 | 登录防护 | IP、账号、设备维度限流和渐进式延迟 |
| AUTH-14 | 安全审计 | 登录、重置、绑定、撤销、停用等事件可追踪 |

### 6.2 P1：首发后优先

- 查看当前设备和其他登录会话。
- 单独撤销某个会话、退出全部设备。
- 修改密码、修改邮箱。
- 绑定和解绑 GitHub。
- 账号停用、注销、恢复期和删除任务。
- 登录提醒、密码变更提醒、邮箱变更提醒。
- 账户数据导出。

### 6.3 P2：增强安全

- Passkey/WebAuthn。
- TOTP 双因素认证和恢复码。
- 管理员强制 MFA。
- 风险登录检测和二次验证。
- 更多身份提供方。

## 7. 核心用户流程

### 7.1 邮箱注册

1. 用户输入昵称、邮箱、密码、确认密码，并同意当前版本服务条款和隐私说明。
2. 前端只做即时体验校验，服务端重复执行全部校验。
3. 服务端执行注册限流和反自动化票据校验；低风险用户无感通过，高风险用户完成
   交互挑战后继续。
4. 服务端规范化邮箱并检查唯一性。
5. 服务端创建 `pending_email` 用户、密码凭据、条款接受记录。
6. 服务端创建同一验证事务下的高熵链接令牌和 6 位数字确认码，只保存带服务端密钥
   的摘要。
7. 邮件任务异步入队，接口不等待真实邮件发送完成。
8. 页面进入等待验证状态，并显示数字码输入框和重发倒计时。
9. 用户可以点击邮件中的验证链接，或在原注册浏览器输入 6 位数字码。
10. 服务端原子地消费当前验证事务，验证邮箱并激活账号；链接和数字码任一成功后，
    另一个立即失效。
11. 同一浏览器仍持有有效注册事务时，可以升级为正式会话；否则要求用户登录。
12. 激活后进入 onboarding。

边界：

- 同一邮箱重复注册返回一致结果，不泄露账号存在状态。
- 新验证邮件发出后，旧令牌失效。
- 验证链接只能使用一次，建议有效期 30 分钟。
- 数字码只用于确认邮箱控制权，不用于无密码登录；建议 10 分钟失效，最多连续错误
  5 次。
- 数字码校验必须绑定不可猜测的注册事务，不能只提交“邮箱 + 6 位码”。
- 未验证账号不得进入学习工作台。
- 长期未验证账号由清理任务处理，不能永久占用资源。

### 7.2 邮箱密码登录

1. 用户输入邮箱和密码。
2. 前端仅校验必填和最大长度，不用注册规则拒绝历史合法密码。
3. 服务端规范化邮箱，执行账号与 IP 双维度限流。
4. 无论账号是否存在，都执行近似等成本的密码校验路径。
5. 失败统一返回“邮箱或密码错误”，不暴露邮箱是否注册、是否停用或是否使用 GitHub。
6. 成功后轮换会话标识，创建新的服务端会话。
7. 服务端通过 `HttpOnly` Cookie 返回会话，不向前端 JavaScript 暴露令牌。
8. 更新最后登录信息并写入认证事件。
9. 若账号未验证，只进入待验证状态；若账号被停用，返回不泄露内部原因的受控提示。

### 7.3 GitHub 快速登录

1. 用户点击“使用 GitHub 继续”。
2. 服务端创建一次性 OAuth 事务，包含随机 `state`、PKCE verifier、过期时间和经过
   允许列表校验的返回路径。
3. 浏览器跳转到 GitHub 授权页。
4. GitHub 回调服务端；服务端验证 `state`，用 PKCE 和客户端密钥交换授权码。
5. 服务端每次登录都重新读取 GitHub 当前用户，使用 GitHub 稳定用户 ID 作为
   `provider_subject`，不使用用户名或邮箱作为外部身份主键。
6. 服务端只申请登录所需的最小权限；如需读取私有邮箱，仅申请 `user:email`。
7. 已存在 `(provider=github, provider_subject=...)` 时，登录对应内部用户。
8. 不存在外部身份时：
   - 有可信、已验证邮箱且未被使用：创建内部用户并绑定 GitHub。
   - 邮箱已对应现有账号：要求证明现有账号控制权后再绑定，不仅凭“邮箱相同”自动合并。
   - 没有可用的已验证邮箱：要求补充并验证邮箱后激活。
9. 登录用途不需要持续调用 GitHub API 时，不保存 GitHub access token。
10. 建立本系统会话并跳转到允许的返回路径。

账号绑定必须遵守：

- 永远不因 GitHub 用户名相同而合并账号。
- 不因未验证邮箱相同而合并账号。
- GitHub 邮箱变化不得静默修改本系统主邮箱。
- 解绑最后一种登录方式前，必须先添加另一种可用登录方式。
- 已登录用户主动绑定 GitHub 时，需要近期重新认证。

### 7.4 忘记和重置密码

1. 用户提交邮箱。
2. 接口始终返回“如果账号存在，我们会发送邮件”。
3. 服务端按邮箱和 IP 限流，并异步发送邮件。
4. 令牌高强度随机、单次使用、限时、只保存摘要。
5. 重置页面设置严格 Referrer Policy，并尽快从地址栏移除令牌。
6. 用户输入两次新密码。
7. 服务端原子地消费令牌、更新密码、提升账号认证版本。
8. 默认撤销该用户全部既有会话。
9. 不自动登录，用户重新走正常登录流程。
10. 向账号邮箱发送密码已变更通知。

### 7.5 修改邮箱

修改邮箱等同于修改账号身份：

1. 要求近期重新认证。
2. 新邮箱必须验证。
3. 变更完成前，旧邮箱仍为主邮箱。
4. 新邮箱验证成功后原子切换。
5. 旧邮箱和新邮箱都收到通知。
6. 变更后撤销其他会话，或至少提升认证版本并要求敏感操作重新认证。
7. 不能把 GitHub 当前邮箱静默同步成主邮箱。

### 7.6 会话与退出

- 当前会话可退出。
- 用户可查看设备标签、创建时间、最近活动时间和大致登录位置。
- 用户可撤销其他会话。
- “退出全部设备”撤销全部会话，并创建一个新的当前会话或要求重新登录，需产品选择。
- 密码重置、账号停用、账号删除立即撤销全部会话。
- 会话达到空闲或绝对有效期后失效。
- “保持登录”只改变服务端会话期限和 Cookie 持久性，不改变权限。

### 7.7 账号注销

1. 要求近期重新认证。
2. 展示将删除的数据范围和不可恢复后果。
3. 立即禁止新建数据并撤销全部会话。
4. 后台任务按用户维度批量删除或匿名化数据。
5. 删除凭据、外部身份、会话、令牌和个人资料。
6. 搜索索引、向量索引、对象存储和缓存必须一起清理。
7. 备份中的数据按备份生命周期自然到期，不能被恢复到线上后重新激活。
8. 同一邮箱再次注册必须得到新的 `user_id`，不能重新绑定旧数据。

是否设置短暂注销恢复期，需要在技术实施前确定。

## 8. 账号信息边界

### 8.1 认证账户应维护

- 内部不可变 `user_id`。
- 规范化主邮箱和展示邮箱。
- 邮箱验证时间。
- 账号状态及状态变更时间。
- 创建、激活、最后登录、停用、删除时间。
- 认证版本，用于批量失效会话和敏感令牌。
- 登录身份：密码、GitHub，未来可扩展更多提供方。
- 会话、认证事件、条款和隐私版本接受记录。

### 8.2 用户资料应维护

- 昵称。
- 头像对象引用，不直接信任任意远程图片 URL。
- 语言、时区。
- onboarding 完成状态可放在学习用户档案，而不是认证主表。

### 8.3 学习档案应独立维护

以下字段不能塞入 `users`：

- 考试日期、目标分数和每日可用时间。
- 当前复习阶段和已学章节。
- 学科、章节、知识点掌握度。
- 学习偏好、计划、错题、练习和复习日程。
- Agent 长期记忆和用户资料。

这些属于学习领域，可独立迭代和删除，不应污染身份表。

### 8.4 不应维护或不应作为主键

- 明文密码。
- 可逆加密的密码。
- 完整 OAuth 提供方响应 JSON。
- 登录用途不需要的 GitHub access token。
- 把邮箱、昵称、GitHub 用户名作为业务外键。
- 把浏览器 `session_id` 当作用户所有权。
- 永久保存无限期 IP、User-Agent 和失败登录明细。

## 9. 用户数据归属原则

### 9.1 唯一事实源

所有用户私有数据的唯一所有者是内部 `users.id`：

```text
GitHub ID / 邮箱 / 密码
          ↓
      auth identity
          ↓
       users.id
          ↓
chat / practice / mistakes / plans / files / agent runs
```

邮箱会变，GitHub 用户名会变，会话会过期，只有内部 `user_id` 稳定。

### 9.2 需要直接或间接绑定用户的对象

直接带 `user_id` 的用户聚合根：

- `chat_sessions` / Agent threads。
- `practice_sessions`。
- `mistake_records`。
- `learner_profiles`。
- `learning_goals`。
- `study_plans`。
- `review_schedules`。
- `user_sources`。
- `user_notes`。
- `agent_threads` 和必要时的 `agent_runs`。

子表可以通过强制外键从聚合根继承归属，例如消息通过 `chat_session_id` 归属用户。
但服务端查询子表时必须通过父表按当前用户过滤，不能把资源 ID 本身当作权限证明。

### 9.3 向量、缓存和文件

- Qdrant 中的个人资料向量必须携带 `user_id` payload，服务端强制注入用户过滤条件。
- 不为每个用户创建一个 collection；使用共享 collection 和强制租户过滤更适合规模化。
- Redis key 应带内部 `user_id` 命名空间，但 Redis key 仍不是授权依据。
- 对象存储路径使用不可猜测的内部 ID 前缀，下载前仍要做数据库授权校验。
- 临时签名 URL 有短有效期，且不能被写入长期日志。

### 9.4 访客数据迁移

当前浏览器会话和公开聊天接口不具备可信所有权，因此：

- 不允许用户仅凭旧 `session_id` 认领历史数据。
- 当前开发演示数据建议直接清理或隔离，不自动迁移到真实账号。
- 若未来正式支持游客模式，必须使用服务端签名的匿名会话 Cookie，并在登录后执行
  一次性、原子的“游客数据认领”。

## 10. 密码与输入规则

### 10.1 注册和修改密码

建议基线：

- 单因素密码最少 15 个字符。
- 最大长度至少 64，产品建议接受到 128 个 Unicode code point。
- 允许空格、Unicode 和常见可打印字符。
- 不强制“大写 + 小写 + 数字 + 特殊字符”组合。
- 不定期强制改密，只在泄露、重置或风险事件后要求变更。
- 阻止常见密码和已知泄露密码。
- 提供密码强度提示，但不展示虚假的“熵保证”。
- 服务端不静默截断，不擅自修改或大小写转换密码。

### 10.2 登录校验

登录表单不能照搬注册密码规则：

- 只校验必填和合理最大长度。
- 不能因后来提高密码规则而拒绝用户输入旧的合法密码。
- 服务端始终执行验证并返回统一错误。

### 10.3 邮箱规范化

- 保存用户输入的展示值和系统比较用的规范化值。
- 去除首尾空白，域名转为规范化形式，产品层面邮箱匹配不区分大小写。
- 不做 Gmail 去点、去 `+tag` 等供应商特定合并。
- 唯一约束建立在 `email_normalized` 上，并使用明确的二进制或大小写规则，
  不依赖数据库默认排序规则。

## 11. 安全需求

### 11.1 会话安全

- 使用密码学安全随机会话标识。
- Cookie 设置 `HttpOnly`、`Secure`、`SameSite`、`Path=/`，生产环境使用
  `__Host-` 前缀且不设置 `Domain`。
- 会话只在 HTTPS 传输。
- 登录、提权和敏感信息修改后轮换会话。
- 服务端保存会话摘要而非明文令牌。
- 同时执行空闲超时和绝对超时。
- 所有认证响应设置 `Cache-Control: no-store`。

### 11.2 CSRF

Cookie 会自动随请求发送，因此所有状态变更接口必须：

- 禁止使用 GET 改变状态。
- 校验 CSRF token。
- 校验 `Origin`，必要时回退校验 `Referer`。
- 只接受受控 JSON Content-Type。
- 精确配置 CORS，不使用通配 Origin 搭配凭据。

### 11.3 防暴力破解和滥用

- 登录按 IP、账号摘要、设备信号组合限流。
- 使用渐进延迟，不使用可被攻击者滥用的永久账号锁定。
- 注册、验证重发和密码重置分别限流。
- 发邮件类入口始终校验无感反自动化票据，达到风险阈值后才显示可见挑战。
- 统一错误和近似统一响应时间，降低账号枚举。
- 邮件发送异步化，避免攻击者用接口拖垮请求线程。

### 11.4 人机校验使用策略

人机校验的目标是提高批量注册、撞库和邮件轰炸的成本，不是抵御网络层或大流量
DDoS。首发采用无感风险判断优先、可见挑战按需出现的策略。

| 入口 | 策略 | 原因 |
|------|------|------|
| 邮箱注册 | 每次校验反自动化票据，风险时展示挑战 | 会创建数据并发送邮件 |
| 重发验证邮件 | 每次校验票据 + 冷却时间 + 总量限制 | 最容易被用于邮件轰炸 |
| 忘记密码 | 每次校验票据 + 通用响应 + 总量限制 | 可骚扰第三方邮箱并消耗邮件额度 |
| 密码登录 | 首次不展示；连续失败或异常流量后要求挑战 | 降低撞库风险且不伤害正常登录 |
| GitHub OAuth start | 默认只限流；异常流量时要求挑战 | 防止 OAuth 临时状态被耗尽 |
| 邮箱链接/数字码确认 | 不要求挑战，执行令牌过期和尝试次数限制 | 避免阻断已证明邮箱控制权的用户 |
| `/auth/me`、退出登录 | 不要求 | 不产生匿名高成本副作用 |
| 已登录学习 API | 不使用 CAPTCHA，按用户设置配额和并发限制 | 应以身份配额保护，而不是人机题 |
| 公开静态页面 | 不要求 | 交由 CDN 缓存和边缘防护 |

强制要求：

- 浏览器挑战结果必须由业务后端向供应商服务端二次校验。
- 票据必须校验有效期、单次使用、场景、站点和预期 action，不能只相信前端回调。
- 反自动化供应商故障时，受保护的匿名写操作不得无保护放行；返回可重试错误且不创建
  用户、不发送邮件。
- 不自行实现图片、算术或滑块验证码。
- 不因为一次验证通过就取消后续业务限流；机器人仍可能通过或购买验证码解题服务。
- 人机校验必须提供可访问性支持，且只收集完成风控所必需的数据。

### 11.5 可用性与抗攻击分层

为了避免机器人、爬虫或恶意请求拖垮服务，需要同时建设：

1. CDN/DDoS 防护和 WAF，在流量到达源站前过滤明显攻击。
2. 网关层连接数、请求速率、请求体大小、上传大小和超时限制。
3. 应用层按 IP、账号、会话、用户和接口分别限流，不能只使用单一 IP 维度。
4. 邮件、解析、Agent 和其他高成本任务异步排队，并限制队列长度、用户并发和预算。
5. 数据库连接池上限、查询超时和慢查询告警，防止应用无限争抢连接。
6. 第三方邮件、OAuth、验证码和模型服务设置超时、熔断和降级。
7. 监控请求量、`429`、挑战失败率、邮件量、队列积压、数据库连接、CPU、内存和错误率。
8. 为注册、邮件和高成本 Agent 功能提供独立紧急开关，受攻击时可以局部停用。

`robots.txt` 只能表达爬取意愿，不能作为安全控制。匿名用户不得直接访问会触发模型、
文件解析、批量检索或邮件发送的高成本能力。

### 11.6 对象级授权

所有用户资源查询使用：

```text
WHERE resource.id = :resource_id
  AND resource.user_id = :current_user_id
```

禁止：

```text
先按 resource.id 查询，再相信前端传入的 user_id
```

必须用两个真实测试用户覆盖读取、更新、删除、导出、WebSocket/SSE 订阅和文件下载。
UUID 只能降低猜测概率，不能替代授权校验。

### 11.7 敏感操作再认证

以下操作要求最近一次认证在短时间窗口内，过期则要求重新输入密码或重新走 GitHub：

- 修改主邮箱。
- 修改密码。
- 绑定或解绑登录方式。
- 退出全部设备。
- 导出全部数据。
- 注销账号。

## 12. 隐私与数据生命周期

### 12.1 最小收集

首发只收集提供服务所必需的信息：

- 必需：邮箱、登录凭据、昵称、认证和安全日志。
- 按功能收集：学习目标、作答、错题、资料和计划。
- 不收集：身份证、精确位置、通讯录、无关社交资料。

隐私说明需列出：

- 收集字段、目的、处理方式和保存期限。
- 邮件、GitHub、云服务等第三方处理者。
- 用户查阅、更正、删除、撤回同意、注销和投诉渠道。
- 数据出境情况及对应合规机制。

### 12.2 未成年人

408 用户通常接近成年，但产品不能默认所有用户都已成年。若允许不满 14 周岁的
用户使用，需要监护人同意和专门的个人信息处理规则。首发可以通过服务条款明确
年龄边界，并在产品决定允许未成年人前完成专项设计。

### 12.3 保存期限建议

| 数据 | 建议 |
|------|------|
| 活跃会话 | 到会话过期或撤销 |
| 已撤销/过期会话 | 短期保留用于安全调查，随后清理 |
| 邮箱验证和重置令牌 | 过期后短期清理，只存摘要 |
| 认证安全事件 | 按安全、投诉和合规需要设固定期限，不无限保存 |
| 邮件投递日志 | 仅保留模板、状态、供应商 ID 和收件人摘要 |
| 用户学习数据 | 账号存续期间或用户主动删除 |
| 已注销账号 | 在线系统完成删除或不可逆匿名化 |
| 备份 | 按固定备份周期自然淘汰，不作为线上恢复账号的来源 |

具体天数需要结合部署地区、合规意见和实际安全运营能力最终确认。

## 14. API 行为要求

- 成功和失败响应格式保持一致。
- 登录、重置、验证接口不泄露账号是否存在。
- `/auth/me` 是前端判断登录状态的唯一事实源。
- 未认证返回 `401`；已认证但无权限返回 `403`。
- 对无权访问和不存在的私有资源，默认统一返回 `404`，降低资源枚举。
- 所有写接口支持请求 ID；关键创建和提交接口支持幂等键。
- API 不接受客户端传入的所有者 `user_id`，所有者来自服务端当前会话。
- WebSocket 和 SSE 建连及重连时都要重新认证和授权。

## 15. 验收场景

### 15.1 正常流程

- 新用户邮箱注册、收信、验证、登录、进入 onboarding。
- 新用户 GitHub 登录、创建内部用户、进入 onboarding。
- 已有用户用密码登录并刷新页面，登录状态仍正确。
- 用户退出后，原 Cookie 不能再访问 API。
- 重置密码后，所有旧会话失效。

### 15.2 账号冲突

- 已有邮箱账号再用同邮箱 GitHub 登录，不会被静默接管。
- GitHub 不返回可信邮箱时，用户必须补充邮箱。
- GitHub 用户名改变后，仍能通过稳定 provider subject 登录。
- GitHub 邮箱改变后，本系统主邮箱不会被静默修改。
- GitHub-only 用户不能解绑唯一登录方式。

### 15.3 安全场景

- 修改浏览器 `localStorage` 不能绕过认证。
- 匿名访问 `/chat` 和历史接口返回 `401`。
- 用户 A 修改 URL 中的线程、会话、练习、资料 ID，不能访问用户 B 数据。
- 猜中 UUID 也无法访问不属于自己的资源。
- 缺失或错误 CSRF token 的状态变更请求被拒绝。
- 重复使用验证或重置令牌被拒绝。
- 过期令牌被拒绝。
- 高频登录和邮件请求被限流，但不能永久锁死受害者账号。

### 15.4 数据删除

- 注销后密码、身份、会话、缓存、对象文件和个人向量都被清理。
- 已删除邮箱重新注册得到新的 `user_id`。
- 新账号不能看到旧账号的任何记录。

## 16. 主要风险与常见坑

1. **只做前端路由守卫。** 前端守卫只能改善体验，攻击者可以直接调用 API。
2. **把 JWT 放在 localStorage。** 一次 XSS 可以窃取长期登录凭据。
3. **把 session_id 当用户 ID。** 会话是临时凭据，不是数据所有者。
4. **只校验是否登录，不校验对象归属。** 这是当前聊天历史接口最直接的风险。
5. **用邮箱或 GitHub 用户名做业务外键。** 两者都可能变化。
6. **仅凭相同邮箱自动合并 OAuth 账号。** 未验证邮箱会导致账号接管。
7. **保存不需要的 GitHub token。** 增加泄露面和撤销复杂度。
8. **密码注册规则用于登录。** 规则升级后会错误拒绝旧账号。
9. **强制复杂字符而忽略长度和泄露密码。** 用户更难用，防护却不一定更强。
10. **错误提示区分“邮箱不存在”和“密码错误”。** 会形成账号枚举。
11. **永久锁定账号。** 攻击者可以批量锁死正常用户。
12. **验证和重置令牌明文落库。** 数据库泄露后可直接接管账号。
13. **Cookie 有 HttpOnly 就忽略 CSRF。** HttpOnly 防读取，不防浏览器自动发送。
14. **OAuth 只校验 code，不校验 state 和 PKCE。** 可能遭受 CSRF 和授权码注入。
15. **开放任意 return_to。** 会形成开放重定向和登录凭据泄露。
16. **硬删除用户时依赖巨型级联。** 大量学习记录会造成长事务和锁等待。
17. **软删除后仍保留唯一邮箱。** 用户无法重新注册，同时可能违反删除预期。
18. **在 JSON 中存核心身份字段。** 无法可靠建立唯一约束和索引。
19. **向量检索忘记 user_id filter。** 会泄露其他用户上传的资料。
20. **日志记录密码、令牌或完整邮箱。** 认证系统自身会成为数据泄露源。
21. **用 IP 变化直接踢用户。** 移动网络、代理和 IPv6 会造成大量误判。
22. **邮件发送与数据库事务强耦合。** 邮件供应商超时会拖垮注册请求。
23. **账号注销只删 MySQL。** Redis、Qdrant、对象存储和备份仍可能保留数据。
24. **管理员和学习用户共用角色字段。** 容易出现普通用户提权到后台。
25. **未定义时间语义。** 所有认证时间必须使用 UTC 和明确精度。
26. **把 CAPTCHA 当成 DDoS 防护。** 它只能降低部分功能滥用，挡不住连接和带宽攻击。
27. **只在前端判断验证码通过。** 攻击者可以绕过页面直接调用 API。
28. **6 位邮箱码直接做 SHA-256。** 数据库泄露后可以穷举，应使用带服务端密钥的
    HMAC、严格次数限制和短有效期。
29. **所有登录都展示可见验证码。** 会伤害可访问性和正常转化，仍可能被解题服务绕过。
30. **只按 IP 限流。** 代理池可绕过，也可能误伤学校、公司和家庭共享出口。

## 17. 待共同决策

1. 认证能力由当前 FastAPI 自建，还是采用托管/自托管身份服务。
2. 会话采用服务端不透明 Cookie，还是短 JWT + 旋转 refresh token。
3. 密码最小长度采用安全基线 15，还是因产品转化先采用 12。
4. “保持登录”的空闲期限和绝对期限。
5. GitHub 同邮箱冲突时，采用重新登录现有账号，还是邮件确认后绑定。
6. 邮箱验证后是否在同一浏览器自动登录。
7. 账号注销是否设置恢复期，以及恢复期长度。
8. 认证安全日志和登录 IP 的具体保存期限。
9. 是否首发允许未成年人注册。
10. 邮件供应商和数据处理区域。

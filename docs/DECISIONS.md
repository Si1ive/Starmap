### 2026-06-06：爬虫优先交付架构

**背景**：
- 项目处于早期开发阶段，但爬虫模块已经同时涉及管理端、后端、数据库、Redis、Scrapy 服务、日志和统计。
- 现有代码中存在字段命名和模块边界不完全一致的问题。
- 如果继续并行开发但不冻结契约，前后端和数据库很容易出现冲突。

**选项**：
- 选项A：继续在 FastAPI 内直接执行爬虫逻辑
- 选项B：FastAPI 负责任务编排，Scrapy Service 负责实际爬取，通过 Redis 解耦

**决策**：选择选项B

**原因**：
- 爬虫任务耗时长，不应阻塞 HTTP 请求链路
- Scrapy 更适合处理下载、限速、重试、反爬和解析管道
- Redis 队列和 Pub/Sub 能解耦任务执行、进度上报和实时日志
- MySQL 作为主存储便于管理端查询任务、日志、统计和采集结果

**影响**：
- `docs/api/README.md` 成为爬虫接口和数据体的真相源
- `backend/scrapy_service` 成为实际抓取服务
- `backend/app/modules/crawler/scrapy_task_bridge.py` 负责请求级任务发布
- `backend/app/modules/crawler/scrapy_event_listener.py` 负责应用级进度和日志事件
- FastAPI 只编排任务，实际抓取能力统一由 Scrapy Service 承担

**负责人**：PM + Backend + Data

### 2026-06-02：技术选型

**背景**：项目初始化，需要确定技术栈

**选项**：

### 2026-06-02：数据库选择

**背景**：需要存储结构化数据、向量数据、缓存数据

**选项**：
- 选项A：单一数据库（PostgreSQL + 插件）
- 选项B：多数据库（MySQL + Qdrant + Redis）

**决策**：选择选项B

**原因**：
- MySQL 存储学科/章节/知识点/题目等结构化数据
- Qdrant 专注向量检索（多模态语料）
- Redis 适合缓存和会话

**影响**：
- 增加运维复杂度
- 需要 Docker Compose 编排
- 各数据库需要独立维护

**负责人**：Backend

### 2026-06-03：后台管理端规划

**背景**：用户询问后台管理端是否在计划内

**选项**：
- 选项A：保持原计划（Week 4-5简单CRUD）
- 选项B：强化后台管理端（完整功能，独立项目）

**决策**：选择选项B

**原因**：
- 管理员需要完整的数据管理能力
- 爬虫任务需要可视化控制
- 系统监控对运维至关重要
- Frontend进度超前，有资源提前启动

**影响**：
- 增加Week 4-5工作量
- 需要新增前端项目（frontend-admin）
- 需要新增25+后端API
- 需要设计权限系统

**具体方案**：
- 前端：独立React项目，Ant Design Pro组件库
- 后端：独立API模块（/api/v1/admin），JWT认证
- 功能：看板、知识点管理、题目管理、爬虫管理、对话管理、监控、配置
- 角色：超级管理员(L3)、数据管理员(L2)、运营人员(L1)

**负责人**：PM

### 2026-06-03：引入 MySQL 作为主存储

**背景**：
- 408 平台需要稳定存储学科、章节、知识点、题目、语料文件、审核记录和任务状态
- 向量检索与结构化存储职责应拆分，避免把检索索引当作唯一事实源

**选项**：
- 选项A：向量库承担主存储与检索双职责
- 选项B：MySQL 作为主存储，Qdrant 作为检索索引

**决策**：选择选项B

**原因**：
- MySQL 适合结构化数据、分页、筛选、审核流和事务一致性
- Qdrant 更适合作为 segment 检索层
- Redis 负责缓存、会话和任务队列，职责边界清晰

**影响**：
- 文档和代码都必须以 `MySQL + Qdrant + Redis` 为主链表述
- 数据结构、检索链与运维说明统一按当前平台收敛

**负责人**：Backend

### 2026-07-15：用户端采用 Web-first Agent 工作台

**背景**：
- 后端语料、检索和管理能力已形成主体，研发重心开始转向学习用户端
- 产品目标不是传统知识库网站，而是围绕 408 场景提供规划、讲解、练习、批改和复盘闭环的 Agent
- 希望学习和实现前沿 Agent 技术，但不希望过早投入桌面安装、签名、更新和跨平台兼容

**选项**：
- 选项A：传统响应式 Web 页面
- 选项B：桌面端优先
- 选项C：Web-first Agent 工作台，按需增加 Tauri 或浏览器扩展能力

**决策**：选择选项C

**原因**：
- 408 Agent 的核心能力依赖服务端工作流、工具、记忆、审批和学习数据，不依赖桌面容器
- 现有 React 用户端可复用，能够先验证学习闭环
- 通过客户端能力接口可以在不分叉业务代码的前提下扩展本地目录、文件监听和浏览器上下文
- 桌面能力以真实工作流触发，不提前承担安装和跨平台成本

**影响**：
- 用户端第一屏改为“今日学习工作台”，不建设营销首页
- 新增公共用户 API、学习用户身份、Agent Runtime 和学习域
- 第一阶段使用 SSE 提供可恢复 Agent 运行事件
- PWA、Tauri 和浏览器扩展均改为按证据启用
- 现有用户端对 `/admin/*` 的依赖需要移除
